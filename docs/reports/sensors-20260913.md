# SM-T630 sensor bring-up — 2026-09-13

## Result

The Galaxy Tab Active4 Pro's Qualcomm SSC sensors are available to Ubuntu
through `net.hadess.SensorProxy`. Live tests passed for the accelerometer,
ambient-light sensor, proximity sensor, magnetometer and derived compass
heading. Automatic ambient brightness is working through GNOME's ordinary
power-settings daemon. Display rotation now uses a debounced, device-specific
controller because the stock relative handler is not reliable on the nested
dummy monitor.

This establishes sensor discovery, measurement, and live physical rotation.
Clean boot is verified. Rotation across two adjacent physical positions passed;
suspend/resume survival and a final four-edge rotation pass remain to validate.

`ubuntu/test-t630-rotation.py` is a bounded physical validator for that gate.
It reads only SensorProxy's `AccelerometerOrientation`, the rotation module's
state file, and GNOME Mutter's current mode/transform; it does not open input
devices, inject events or change display configuration. A pass requires at
least two real non-flat orientations, two Weston transforms, matching GNOME
dimensions, Mutter transform zero, and no mismatch after a 1.5-second settling
interval. A 180-second lens-up/flat run on boot
`84251a48-c3c6-44cf-81bf-5d9f046fb4f8` observed only `undefined` with transform
0 and correctly returned failure rather than treating an unmoved tablet as
rotation evidence.

## Device-specific work

Samsung's 5.4 kernel exposes `/dev/adsprpc-smd-secure` with the downstream
FastRPC ABI. The packaged `hexagonrpcd` adds the legacy GETINFO, sensor-domain
attach, invoke and mmap layouts needed by that ABI. `iio-sensor-proxy` also
watches the downstream `fastrpc` subsystem so it can bind the SSC drivers.

Only the read-only sensor configuration and DSP runtime files from the exact
DZE3 stock image are used. Generated SSC registry state lives under
`/usr/local/share/t630/sensor-hexagonfs`; the Android persist partition is not
modified. The SM-T630 uses the upstream `ambient_light` sensor endpoint, not
the S9 Ultra port's `auto_brightness` endpoint.

## Installed pieces

- `libssc` 0.4.4-t6302
- `hexagonrpcd` 0.4.0-t6302
- `iio-sensor-proxy` 3.9-t6302
- `/usr/local/sbin/t630-sensors-start`
- `/usr/local/libexec/t630-session-manager`
- `/etc/udev/rules.d/61-t630-sensors.rules`
- `/etc/polkit-1/rules.d/49-t630-sensorproxy.rules`

The tablet's custom desktop startup launches the sensor stack after audio has
finished attaching to the shared ADSP. A short accelerometer probe primes SSC
discovery before the desktop proxy starts.

The custom login session now provides the small SessionManager interface that
GNOME's power daemon expects, starts that daemon after
`/run/t630-sensors-ready`, and grants the dedicated `tablet` account permission
to claim the read-only SensorProxy streams. Automatic system suspend remains
disabled; the existing guarded Power-button suspend path is unchanged.

`t630-rotation-controller` locks Mutter's built-in relative rotation handler
and waits one second for each accelerometer position to settle. It then changes
the real `DSI-1` output through `t630-rotation.so`, changes the rootful Xwayland
screen dimensions, and selects the matching mode on the verified Mutter
`LVDS1` identity. Mutter itself remains at transform zero. The calibrated
Weston map is `normal` → 0, `left-up` → 1, `bottom-up` → 2, and `right-up` → 3;
even values use 1200×1920 and odd values use 1920×1200. Flat/undefined readings
are ignored.

The Weston module is original, redistributable source in
`ubuntu/t630-weston-rotation.c`. On Ubuntu 24.04 it builds with
`libweston-13-dev` by running `tools/build_t630_weston_rotation.sh`; install the
result as `/usr/lib/aarch64-linux-gnu/weston/t630-rotation.so`. The runtime does
not depend on the development headers or `xcvt` because the verified portrait
modeline is fixed in the controller.

## Live evidence

- Accelerometer: roughly -0.22, -0.40, 9.79 m/s² while lying flat
- Ambient light: 8–9 lux in the test room
- Proximity: FAR
- Magnetometer: changing three-axis readings around 45 µT
- Compass: stable 275–278° heading
- Idle proxy sample: zero user CPU ticks over five seconds
- Automatic brightness: GNOME reacted to 8–9 lux and selected roughly 78–80%
  brightness without oscillation

Audio, Bluetooth, battery reporting and the GNOME session remained healthy
during the live sensor tests.

An early inner-monitor-only test held `left-up` in standard landscape, then
moved to `bottom-up` portrait and proved that the absolute controller stopped
the stock handler's feedback loop. It also exposed that changing only Mutter's
dummy monitor could not rotate or resize the real scanout.

The completed path was then tested live in `bottom-up` portrait. The validator
observed Weston transform 2, Xwayland and GNOME at 1200×1920, Mutter transform
zero, and no mismatch. The view-only screen service was also changed to undo
the current real-output transform instead of always forcing its frames to
landscape. Hiding Weston's fallback panel removed the last recovery-UI strip
from the portrait GNOME screen. Standard landscape is the adjacent `left-up`,
Weston-transform-1, 1920×1200 position; a final multi-position run is retained
as the acceptance gate rather than inferred from this single stable sample.

## Clean-boot evidence

Boot `03e0d0bc-2443-4226-9823-81db41c213e7` automatically restored GNOME,
Wi-Fi access, the speaker sink at 30%, the Bluetooth controller and BlueZ,
`hexagonrpcd`, and `iio-sensor-proxy`. SensorProxy reported accelerometer,
ambient-light and proximity support. The session bridge reported active, the
GNOME power daemon claimed the light sensor without a manual monitor, and the
kernel logged successful ADSP startup with no sensor timeout or crash.
